# 工作台选路与交接方法

本指南是重新整理的操作说明。示例均为虚构，不代表用户实际经历或经验证的业务结果。

完整能力列表以本库 SKILL.md 为准；本手册展示常见入口和通用交接方法，不要求安装所有可选扩展。

## 一、按交付物选路

识别请求中的动词和对象，而不是只抓关键词。相同素材可以支持不同任务，用户要什么产物决定先使用哪个技能。

| 用户实际想得到什么 | 起点 | 什么时候停 |
| --- | --- | --- |
| 说明服务谁、解决哪一步 | 价值定位 | 能写出有依据的承诺与一个验证动作 |
| 判断是否有人愿意购买、自己能否交付 | 小生意验证 | 有可执行试验和继续/暂停条件 |
| 改善已有联系或交付后的关系 | 信任关系 | 有对方需要的帮助及适当回访安排 |
| 从材料中提炼可复用判断 | 洞见卡 | 有来源、机制、动作和失效条件 |
| 用学习解决当前具体卡点 | 项目式学习 | 有与问题相关的知识和最小尝试 |
| 让已有笔记能被任务调用 | 知识工作流 | 跑通材料到调用结果的一个样例 |
| 形成能说出口的完整表达 | 短视频脚本 | 有事实支持、适合目标时长的稿件 |
| 学会参考内容的有效结构 | 内容拆解迁移 | 能分清观察、机制假设和自己的新证据 |
| 判断下一轮内容该改什么 | 内容实验 | 有口径清楚的观察和一个主要变量 |

先交付当前产物，不把全套目录当成任务清单。

## 二、容易混淆的边界

### 定位与验证

定位解决“想服务谁、可能提供什么价值”；验证解决“什么行为能支持或推翻这个想法”。十条评论能启发定位，不能直接证明十人愿意购买。用户已有具体产品时，可以直接做验证。

### 洞见与脚本

洞见卡保留条件、机制、反例，追求能被再次调用。脚本围绕一个观众组织表达，追求看得懂、说得出。卡片没有真实案例时，脚本可以解释方法，不能自动编成第一人称成功故事。

### 拆解与实验

拆解能说明一段内容如何组织，以及它为什么可能起作用。实验用新的观察检查某个解释是否值得保留。没有后台数据的拆解仍能成立，但不能宣称已经证明传播效果。

### 学习与建库

需要理解一个概念时，不必先建知识库。需要解决找不到材料的问题时，先改善检索与调用；目录整齐不能证明已经理解知识。

### 关系与交易

提供帮助、获得关注、产生询问、愿意购买、满意交付分别记录。不要把一个阶段的行为升级为下一阶段的证据。一次性业务不必为了使用某个技能而增加订阅或社群。

## 三、选择最小路径

先写出一句交付要求：给谁、交付什么、什么时候可用、有哪些限制。

已有材料足够时直接执行；缺少会改变判断的事实时提出最少的关键问题。可以先做不依赖缺口的部分，但不能把假设悄悄改写成用户事实。

串联只发生在上一步产物确实能成为下一步输入时。例如已提炼出一个带来源的判断，再改成解释型稿；不能仅为了“流程完整”而要求用户先做定位、访谈、建库和商业计划。

## 四、交接卡模板

跨技能时保留以下信息，按任务需要合并字段：

```text
目标产物：本轮最终要交付什么。
用户约束：时间、形式、预算、明确不做的事项。
已知事实：用户给出的经历、实际数据及材料位置。
假设：仍待验证的解释或预期。
上一步结果：已经产出的判断、清单或稿件。
下一步用途：为什么这个结果值得交给下一项技能。
缺口：不能自行补写的内容。
完成标准：本轮怎样算交付，不等同于未来效果保证。
```

没有实际读取的材料不能放进“已知事实”；来源找不到时保留缺口。

## 五、完整示例：只要一份口播

虚构输入：某设计师交接时只发截图，同事第二天找不到文件；后来试着整理一页文件入口，但还不知道长期效果。用户只要45秒口播，不做定位、不建库。

选择：直接使用脚本技能。

交接信息：

- 事实：发过截图、同事找不到文件、改成一页入口、长期效果未知。
- 假设：清晰入口可能有助于接手；还没有对比数据。
- 产物：围绕“交接要给可用入口”组织的一份口播。
- 边界：不能补写节省了多少时间、同事满意或工作效率提高。

完成后停止，不把稿件自动写成知识库资产，不追加商业定位。

## 六、完整示例：笔记想支持一次服务试验

虚构输入：用户有三条客户访谈记录，想测试一项项目交接整理服务，每周可用4小时，没有成交记录。

第一步先读访谈，分开客户原话与个人解释。如果问题和服务对象已清楚，直接用小生意验证；只有定位仍模糊时才先形成候选定位。

可能产物：一份明确输入、输出、边界和报价假设的试验说明。三个访谈不能变成“市场已验证”；免费使用反馈不能代替按报价购买。

只有用户需要对外表达时，再把试验说明转成内容稿。传播计划不是发送或收款授权。

## 七、结果不确定时怎么交付

将结论分别写为：可以确定、暂时假设、当前无法判断。给出最值得补充的一项证据或一个可开始的动作。

如果所选专项技能没有安装，先指出缺失名称；可提供本指南支持的初步结构，不假称已经运行完整技能。获取和安装依照用户请求进行。

## 八、完成检查

- 交付物是否正是用户要的东西？
- 是否加载了不必要的技能，或创建了没有使用需求的文件？
- 上一步的猜测是否在下一步被当成事实？
- 是否能说明现在停在哪里，以及什么证据值得继续？
- 计划与执行、估算与实测、观察与因果是否分开？
